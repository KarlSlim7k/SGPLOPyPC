### 2. Base de Datos - Modelo del Proveedor
La plataforma modela al proveedor en la tabla **`proveedor`** con las siguientes características:
**Campos principales:**
- `id_proveedor`, `id_usuario` (FK a tabla `usuario`)
- `nombre_empresa`, `representante_legal`, `registro_fiscal` (RFC), `domicilio`, `telefono`
- `especialidad` (texto libre, ej. "Construcción")
- `estatus` → `PENDIENTE` | `VALIDADO` | `RECHAZADO` | `SUSPENDIDO`
- `fecha_registro`
**Relaciones clave:**
- **`usuario`**: El proveedor es un usuario con `rol = 'PROVEEDOR'`
- **`participacion`**: Inscripciones a licitaciones
- **`propuesta`**: Propuestas técnicas/económicas enviadas
- **`contrato`**: Contratos adjudicados al proveedor
- **`documento`**: Documentos legales (`DOC_LEGAL_PROVEEDOR`)
**Migraciones aplicadas:**
- Migración `004_fase6_publico_completo.sql` extendió la tabla agregando `regimen_fiscal`, `contacto_cargo`, `contacto_email`.

Observaciones de APIs:
- No existe endpoint GET /api/v1/participaciones (responde 404), aunque sí existe POST para crear participaciones.
- El registro público valida: email único, RFC único, contraseña mínimo 8 caracteres, y aceptación de términos (terms).
- Durante las pruebas, se detectó que el payload con "terms": true fue rechazado por el backend con el mensaje: "Debes aceptar los términos de uso y aviso de privacidad", lo que sugiere que el campo podría estar esperando un formato diferente o que la validación del frontend no coincide exactamente con la del backend en ciertos edge cases.

9. Conclusión
El rol PROVEEDOR / CONTRATISTA se encuentra funcionalmente implementado y operativo en producción. El flujo completo (registro → validación → inscripción → propuesta → adjudicación → contrato) está codificado y activo. La base de datos, las APIs de backend y los frontends (tanto público de registro como administrativo de gestión) están alineados y funcionando.
Los principales puntos de atención son:
1. El proveedor demo en producción tenía estatus SUSPENDIDO al inicio de esta auditoría (se cambió a VALIDADO como parte de la prueba de funcionamiento del endpoint admin).
2. Existe un error 500 persistente en el módulo de soporte/tickets.
3. La discrepancia entre el conteo de proveedores en el panel admin vs. las estadísticas públicas puede generar confusión administrativa.
4. No hay un endpoint de listado general de participaciones disponible para admin (404).

10. Actualización Posterior - Hardening PROVEEDOR (2026-05-08)
Cambios aplicados sobre el flujo del rol PROVEEDOR / CONTRATISTA:

1) Registro público - términos y privacidad
- Se normalizó la validación para aceptar `accepted_terms` (canónico) y `terms` (legacy).
- Si ambos vienen en payload, prevalece `accepted_terms`.
- Se mantiene validación estricta: debe ser `true`; de lo contrario responde 422 con el mismo mensaje de términos.

2) Participaciones - endpoint administrativo general
- Se incorporó `GET /api/v1/participaciones` (solo ADMINISTRADOR).
- Incluye paginación y filtros: `page`, `limit`, `licitacion`, `estatus`, `q`.
- El endpoint existente `GET /api/v1/licitaciones/{id}/participaciones` se mantiene sin cambios.

3) Estadísticas públicas de proveedores
- Se amplió `GET /api/v1/public/estadisticas` con:
  - `proveedores_registrados_total` (todos los estatus).
  - `proveedores_activos` (`PENDIENTE` + `VALIDADO`).
- Se conserva `proveedores_registrados` por compatibilidad y se mapea al total.
- La landing pública ahora consume `proveedores_registrados_total` (con fallback a la clave legacy).

Resultado del hardening:
- Quedan resueltas las brechas funcionales de términos de registro, 404 de participaciones generales y discrepancia de criterio público/admin para conteo de proveedores.

Ajuste técnico complementario aplicado en producción:
- Se corrigió el filtro `q` de `GET /api/v1/participaciones` para evitar error 500 causado por reutilización de placeholders SQL en búsquedas múltiples.
- Se agregó compatibilidad de inserción en registro público de proveedor para entornos con diferencias de esquema (con y sin columnas extendidas de Fase 6), manteniendo el mismo contrato funcional del endpoint.

Actualización de experiencia de rol PROVEEDOR:
- El login de usuarios con `rol = PROVEEDOR` ahora redirige a `/frontend/proveedor/centro.html`.
- Se habilitaron módulos frontend iniciales del proveedor:
  - Centro del proveedor (`/frontend/proveedor/centro.html`) con acceso a notificaciones.
  - Convocatorias del proveedor (`/frontend/proveedor/convocatorias.html`) con inscripción directa a licitaciones permitidas.

Actualización de módulo Mis participaciones:
- Se incorporó `GET /api/v1/participaciones/mias` para proveedores autenticados.
- El endpoint devuelve historial propio con datos de licitación, estatus de participación y datos básicos de propuesta cuando existe.
- Se habilitó `/frontend/proveedor/participaciones.html` y acceso desde el centro del proveedor.
